What the spec actually demands

Two conjuncts, and they bind both the artifacts and the demo

§8 Required Demo Scenarios, item 4

“Show how the generated Slack-style updates affect the brief, including at least one cited generated update.”

§3 Mandatory Data-Generation Subtask

“Add useful account-team context that is not fully duplicated from the provided Salesforce, Gong, pricing, or policy files.”

“Across the generated updates, include at least one update that reinforces a known fact, one that adds missing context, and one that introduces ambiguity or a possible conflict the system must handle.”

§4 System Requirements

“Run the system with live LLM calls to generate the briefs, approval outputs, traces, and other generated artifacts included in the submission.”

§9 Deliverables, D · and §6

“Sample run artifacts: generated briefs, generated Slack-style update data, approval-flow output, and trace or log examples.”

“For the interview, be prepared to run a live demo that also makes live LLM calls rather than replaying only precomputed or mocked responses.”

Determination — stated plainly, because everything else follows from it

  • A Slack entry appearing in Source Evidence is NOT sufficient. §8.4 has two conjuncts joined by “including”. A bibliography row satisfies “at least one cited generated update” literally and satisfies “affect the brief” not at all. The bar is stage (e), not stage (d).
  • It must demonstrably change something, and be cited where it does. A Slack evidenceId must appear on a claim inside a substantive section — an executive summary, a buyer goal, a negotiation risk, a stakeholder, or an action's rationale — not only inside sourceEvidence.
  • It binds BOTH. §9.D makes the sample artifacts a deliverable and §4 requires they come from live runs, so a shipped brief must carry it; §6 requires the live demo to reproduce it. Passing one and not the other is a partial submission.

What is genuinely still open

One broken thing, one structural quirk, one honesty note

Broken The checked-in samples

pnpm eval:brief-quality exits 1 with 16 violations against samples/. Two of them are literally “Source Evidence cites no slack evidence although the authorized manifest reaches it.” normal-opportunity-brief.json cites one source type (crm).

These artifacts were exported before every fix above. They are the only reason any part of Scenario 4 is unmet on the submission as it currently stands.

Variance OPP-1001 is the weak cell

(e) passes 2 of 5 for OPP-1001 versus 4 of 4 for both other deals — and samples/normal-opportunity-brief.json is OPP-1001.

The cause is content, not code. Per generation.json, SLK-9003 is OPP-1001's ambiguity_or_conflict row — and it is source_access_level = sensitive_pricing, while USR-5001 has can_view_sensitive_pricing = false. So OPP-1001's only reachable Slack content is reinforces a known fact and adds missing context: the two least decision-shaping kinds.

This is correct permission behaviour, not a defect. OPP-1003/USR-5003 can see its conflict row, which is exactly why it passes (e) 4/4 on the Executive Summary.

Note Stage (d) is partly instructed

The strategy task added at 18:44 says: “add one for each remaining record that supports the deal, including the Slack account-team updates…”

That is a mild thumb on the scale for the bibliography. It is defensible — each entry must still quote its own record and pass validation, so it produces a complete evidence list, not a fabricated finding. But it means (d) alone should never be quoted as proof of Scenario 4.

Nothing instructs (e). That is what makes 10/13 meaningful.

The decision

Four options — two already shipped, two to reject, one to do

Option 1 — Reserve context for Slack; instruct the strategy agent to preserve a Slack-backed finding Reject

The prior agent's proposal.

  • It is already half-shipped, as the sourceEvidence instruction at 18:44 — which is precisely why (d) is not usable as evidence for §8.4.
  • Going further crosses the line. “Preserve a relevant non-duplicative Slack-backed finding” sounds conditional, but the model is the only judge of “relevant”, and it has just been told the answer the operator wants. The condition collapses into a quota.
  • Where the line sits: instructing coverage of the evidence list is fair representation — it changes what gets enumerated, not what gets concluded. Instructing a finding be carried into a conclusion is a forced citation — it changes the analysis to satisfy a demo.
  • It would destroy the result it is meant to produce. Right now the honest claim is: the model chose the Slack update on relevance, unprompted, in 10 of 13 runs. Add the instruction and that sentence can never be said again — the project's entire thesis is grounded, unforced output.

Unnecessary (it already passes without it) and actively harmful to the submission's central claim.

Option 2 — Per-source-type retrieval floors, no prompt instruction Already shipped, and working

  • The parent asked whether the existing gong_transcript cap is doing its job. Measured answer: yes, decisively. It is the single change that turned this requirement around.
  • Slack moved from rank 13 of 27 to rank 1–3 of 22; context share from 1.26% to 3.87–6.88%; admitted Slack rows from 1 to 2–3.
  • All six source types now share the same non-primary candidate window of 2, so no source can accumulate fusion mass by sheer count. Retrieval recall was checked against pnpm eval:deterministic when it landed.

Nothing left to do. This option is spent — it is the fix.

Option 3 — A UI button that regenerates a new Slack evidence set and shows how the brief changes Reject for this submission

Assessed seriously — it is the most direct reading of §8.4, and it would exercise the Mandatory Data-Generation Subtask live. But:

  • The demonstration already exists at zero cost. samples/slack-impact-comparison.md documents a real A/B: the same opportunity, same persona, same live pipeline, run twice with only can_read on the Slack permission grant flipped — showing the Slack chunk mechanically leaving the pool and the next-best candidate backfilling it. That is a cleaner controlled experiment than regeneration, because regeneration changes the content and the ranking at once.
  • Cost is not small. A button means a generation endpoint, fixture write-back, corpus re-embedding, cache invalidation, a diff view, and its own permission story — a day-plus of work touching apps/api, apps/web and the ingest path.
  • The risks are concrete. Re-embedding mid-demo is slow and can fail live; evals/golden-retrieval.json pins expected retrieval against the current fixtures and would break; runs_one_active_opportunity_uq makes “regenerate then immediately re-run” collide with an in-flight run; and a fresh generation could produce a Slack set that happens not to change the brief, turning the headline demo into a coin flip in front of a reviewer.
  • It also weakens reproducibility, which §4 explicitly asks for (“replayable traces… consistently across runs”). Mutating the corpus from the UI makes the checked-in artifacts unreproducible.

Genuinely good post-submission idea; wrong thing to build the day the requirement already passes.

Option 4 — Regenerate the sample artifacts Recommended

  • It is the only thing actually broken. 16 violations, two of them the Slack rule itself.
  • It requires no code change, no prompt change, and no new surface — the pipeline that produces a passing artifact already exists and was just measured 13 times.

Option 5 — The addition I would make to Option 4 Do this too

  • Gate sample check-in on stage (e), not stage (d). The brief-quality eval currently enforces “Source Evidence cites slack” — that is (d), and (d) is partly instructed. A regenerated OPP-1001 artifact could pass the eval and still fail §8.4, because (e) is 2-in-5 for that deal.
  • Be aware there is no automated gate for (e) today. brief-quality.ts rule 3 reads entry.sourceType on sourceEvidence entries only — so pnpm eval:brief-quality passing is not evidence that §8.4 is satisfied. Until something checks it, the check is this one-line predicate over the exported brief JSON:
    any claim outside sourceEvidence carrying a citation whose evidenceId starts with "slack:"
    Sections to walk: executiveSummary, buyerGoalsAndBusinessDrivers, negotiationState, stakeholderMap (including each stakeholder's own claims), and recommendedNextActions.actions[].claims. Reporting it as a defect only, per instruction — no eval rule was added.
  • (d) is 13/13 at “≥1 Slack row”, but not at “every Slack row”. In one OPP-1003 run, SLK-9008 was cited elsewhere in the brief yet did not get its own Source Evidence entry, despite the prompt asking for one per record. Harmless for §8.4, worth knowing before anyone describes Source Evidence as an exhaustive manifest listing.
  • Source the Scenario 4 evidence from OPP-1003 (or OPP-1002). §8.4 does not name an opportunity, and OPP-1003 passes (e) 4/4 with the ambiguity_or_conflict update carrying the Executive Summary — the strongest possible demonstration, and it doubles as the Scenario 2 approval-routing artifact.
  • Point the reviewer at the existing badge. deal-workspace.mapper.ts:443 already computes accountTeamUpdateImpact per section by resolving citations to sourceType === 'slack', and deal-brief.tsx renders it as an “Account-team update impact” badge. On a passing OPP-1003 run that badge lights up on Executive Summary and Negotiation State — not merely on Source Evidence. That badge is the stage-(e) instrument, already shipped and already wired into the guided tour.

Recommendation

Do not change application behaviour. Fix the artifacts, and gate them on the right measurement.

  1. Ship no code change for this requirement. Options 1 and 3 are both rejected. The retrieval fix (Option 2) already landed and is measurably doing the work.
  2. Regenerate samples/ from live runs on current HEAD — this is already in flight in another session, so this is a message to that work rather than a new task.
  3. Tell that agent to check stage (e), not just the eval. Before checking a brief in, confirm at least one slack: evidenceId appears on a claim outside sourceEvidence. Passing pnpm eval:brief-quality is necessary but not sufficient for §8.4.
  4. Make OPP-1003 the Scenario 4 exhibit. 4/4 on (e), with the conflict-introducing generated update carrying the Executive Summary.
  5. Update samples/slack-impact-comparison.md's conclusion. Its A/B experiment is still valuable and should be kept, but its headline finding — “no finalized brief contains a Slack citation” — and its “what would change this” recommendation both describe a code state that no longer exists. Shipping it as-is tells a reviewer the system fails a requirement it passes.
  6. Say the variance out loud in the technical overview. 10/13 is a real and defensible number for an LLM-synthesised brief, and stating it is far stronger than implying determinism. Presenting the honest distribution is more convincing to this particular reviewer than a suspiciously perfect one.

Method. 13 live OpenRouter runs (google/gemini-3.5-flash-lite, provider openrouter, nonzero token usage on every call) driven through the production workflow — authorized retrieval, three specialists, strategy synthesis, and the same grounding validation — by a probe adapted from scripts/brief-quality-live.ts onto its own randomly-named throwaway database, migrated and ingested from fixtures/cato and dropped afterwards. Neither slacato_demo nor the Railway deployment was touched. The one measurement mechanic: because runs_one_active_opportunity_uq treats awaiting_approval as active, each run's status was set to cancelled on the throwaway database after all of its data had been captured, so the next iteration for the same opportunity could start. No application source, samples/, docs or README were modified, and nothing was committed.
