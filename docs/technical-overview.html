01 · Business context

One brief for the moment before a negotiation.

A seller preparing for a commercial negotiation has to reconcile CRM facts, recent calls, stakeholder dynamics, account-team updates, pricing notes, and deal-desk policy—often under time pressure and with different access rules for each source. The system accepts an opportunity and requester identity, assembles the evidence that person is allowed to use, and produces a concise preparation brief with traceable support.

The objective is not autonomous negotiation. It is decision support: surface the buyer’s goals, the current commercial state, risks, stakeholders, missing information, and next actions while making uncertainty visible. Pricing, legal, customer-facing concessions, and low-confidence material remain subject to deterministic policy and human authority.

Reduce preparation time

Fan out focused analysis across conversation, stakeholder, and commercial evidence, then synthesize one coherent brief.

Keep evidence inspectable

Claims link to immutable authorized evidence; API and UI render stable labels such as source=<file>, id=<value>.

Keep people accountable

If a recommendation needs approval—for example, a large discount—the brief waits for the right person to approve or reject it.

02 · Architecture

Thin apps around durable domain and infrastructure seams.

The browser requests work. The API checks access. The worker builds the brief. Core holds the business rules; infrastructure connects them to storage, queues, search, and models.

Logical view

Deployment view

The API proves who may request work, the worker performs it, PostgreSQL preserves the history needed to recover it, and the model gateway contains external model access.

Why one browser origin?

The web gateway serves the interface and forwards API calls under one origin, so secure session cookies do not need cross-origin exceptions.

Why split API and worker?

The API can answer quickly after recording a command. Slow retrieval and model calls happen in the worker and can retry without holding an HTTP request open.

Why does PostgreSQL own recovery?

Workflow state and checkpoints survive process or queue loss. Redis can be cleared and rebuilt without losing which step should run next.

Why one model gateway?

Every provider call crosses one boundary where budgets, retries, validation, and diagnostics can be applied consistently.

03 · Persisted data model

Actual Drizzle schema, grouped by responsibility.

The model separates permissions, evidence, workflow, and outputs so access is checked before retrieval, interrupted work can resume, and every generated claim can be traced to the exact evidence version that supported it. Read the groups from identity and deals through evidence, workflow, and final artifacts; arrows point from a record to the parent it depends on. Hover over any table name or field row for a plain-language explanation.

Identity and deals

People, accounts, opportunities, and permission grants establish who is asking and which deal data they are allowed to use.

Evidence and retrieval

Source records become immutable evidence versions. A run freezes its authorized search results into a manifest so later citations cannot silently point at different content.

Durable workflow

Runs, commands, leases, checkpoints, and generation attempts record what should happen, what already happened, and where processing can safely resume.

Artifacts and review

Specialist outputs become claims and citations. Policy-sensitive drafts create approval requirements and immutable decisions before the final brief is stored.

Immutability is part of the data model. Database triggers reject updates/deletes to source and evidence versions, manifests, approval decisions, and approval requirement entries; finalized briefs are immutable. Manifest entries preserve content hashes, citation IDs, locators, source/sensitivity, component ranks, adjustments, and included character counts.

The drawing deliberately omits bookkeeping tables and authorization views that do not change this core flow. They support budgets, audit history, approval membership, and safe database access without adding another business concept to the diagram.

04 · Run lifecycle

Eleven states, six steps, one command at a time.

A run is a durable state machine, not a free-running model graph. Each step is dispatched as an idempotent command, claimed under a lease, and committed together with the next command in a single transaction. What a model returns decides what the brief says; it never decides what happens next.

Created

The system accepts the authorized request, creates the run, and records the first durable command. No model is involved.

Retrieving

The worker searches only evidence the requester may read and freezes the selected versions into a manifest for this run.

Specialists running

Conversation, stakeholder, and commercial specialists analyze the same frozen evidence in parallel and save their outputs separately.

Synthesizing

The strategy agent combines those specialist outputs and authorized evidence into one structured draft brief.

Validating

Ordinary code checks the draft’s schema, citations, safety rules, and approval policy. The model cannot choose the next state.

Awaiting approval

If policy requires human authority, the run pauses until every required decision is recorded against the unchanged draft.

Finalizing and completed

The system rechecks the approved draft, stores an immutable brief, and makes its evidence and timeline available for review or export.

Rejected, failed, or cancelled

A human rejection, unrecoverable processing error, or requester cancellation ends the run. Terminal runs cannot accept later workflow events.

Recovery loop

If a worker stops unexpectedly, ownership expires and another worker continues from the saved checkpoint. Completed work is not regenerated unnecessarily.

Deterministic codeModel callHuman decisionTerminal

Three of the six steps touch a model — retrieve embeds the query, specialists and synthesize generate. start, validate, and finalize are ordinary code. Nothing a model returns can change which state comes next — the transition table above is exhaustive, and an event that is not in it raises InvalidRunTransitionError instead of moving the run.

Where authorization sits in the run

This view follows the information rather than the worker states. The request is authorized before search, the selected evidence is checked again before any model sees it, and the generated draft must pass citation and policy checks before delivery.

Request and first permission check

The API binds the authenticated person to the requested opportunity and limits eligible evidence by account, source, restriction, and sensitivity.

Authorized retrieval

Keyword and semantic search run only over allowed rows. Ranking improves relevance; it never expands what the requester may see.

Second permission check

Immediately before a model call, the worker recomputes the authorization binding and compares it with the frozen manifest to catch stale or substituted context.

Specialists and synthesis

Three specialists produce focused analyses, then the strategy agent combines them with the authorized evidence into one draft.

Citation and policy checks

Code verifies that every claim is supported and determines whether pricing, legal, concession, conflict, or confidence rules require human approval.

Human decision and delivery

Required authorities approve, edit, or reject the unchanged subject. Only a valid decision set can produce the immutable brief shown to the seller.

Partial failure is intentionally asymmetric. Conversation and stakeholder failures become schema-valid degraded artifacts with warnings and omitted dependent claims. The commercial specialist is policy-critical; its failure stops the run rather than allowing pricing/legal analysis to disappear silently.

05 · How and why

Models propose. Deterministic code governs.

Durable workflow over model orchestration

The fixed sequence—start, retrieve, specialists, synthesize, validate, finalize—lives in a Postgres-backed workflow and outbox with checkpoints and versioned transitions, so retries, recovery, idempotency, and operator inspection are testable. No model is ever asked what should run next.

Two independent permission gates

Authorized SQL relations and predicates restrict rows before lexical or vector search. Immediately before every LLM call, assertAgentContextBindings recomputes the binding and compares its scope hash to the immutable manifest, catching stale or substituted contexts.

Rule-based approval triggers

Discount thresholds, renewal uplift, legal concepts, customer-facing concessions, confidence, conflict, and missing evidence are classified by provider-independent code. A model cannot self-declare that its recommendation is safe enough to skip approval.

Per-claim citation validation

Generated citation tuples are canonicalized to code-owned manifest values. assessClaimSupport checks that referenced evidence exists and that the claim’s material names, amounts, dates, predicates, polarity, and bounded paraphrase are supported; unsupported claims are rejected or removed.

Hybrid RRF retrieval

PostgreSQL full-text ranking and exact pgvector cosine ranking are fused by stable evidence ID with reciprocal-rank fusion (k = 60). Reliability and age adjustments are transparent and capped at ±0.02; mandatory policy and exact CRM grounding are packed separately so top-k competition cannot erase them.

Typed, schema-validated artifacts

Conversation, stakeholder, commercial, and strategy outputs have strict Zod contracts, bounded arrays/text/serialized size, structured repair, and provider-neutral model interfaces. The serialized-size ceiling is per-artifact, not one shared constant: conversation and commercial cap at 6,000 bytes, but a realistic five-person stakeholder map — each person nesting its own claim and citation objects, unlike the flat string-array shape of the other two — genuinely needs more room, so the stakeholder specialist gets its own 8,192-byte ceiling. Under the old shared cap, exceeding it triggered a schema-repair retry that returned a smaller, less-grounded artifact and hollowed the brief’s Stakeholder Map section. Strategy returns the canonical nine-section DealBrief rather than a second divergent format.

Citation shape, precisely: the brief contract has nine required top-level sections. Factual sections expose claims directly or through their typed child records (stakeholders, recommended actions, and evidence summaries). missingInformation is intentionally questions, not asserted claims; review warnings reference existing claim IDs. The renderer only exposes generated output after every referenced evidence ID is authorized.

Retrieval details

  • An immutable manifest binds the run, requester/deal scope hash, policy hash, full query/plan hash, embedding provider/model/dimension/version/normalization, context limit, and diagnostics.
  • The plan runs the requester’s query plus six fixed section-oriented searches (deal snapshot, buyer goals, stakeholders, negotiation state, next actions, missing information), each scoped to the source types that can answer it, then fuses the results. Every non-primary source type — gong_summary, gong_transcript, pricing, salesforce, and slack — is capped to 2 candidates per search so none can win by sheer count; Salesforce and gong_transcript each used to reuse an unrelated completeness/limit constant as this cap instead, so they entered every search unfiltered. gong_transcript was the more severe case: on a measured OPP-1001 run at production limits it filled 84.7% of prompt context, crowding gong_summary and pricing out of the pool entirely and leaving only 4 of the 6 source types represented. Capping it the same way as every other source restored all 6.
  • Lexical matching scores partial concept overlap instead of gating on every query term appearing in one chunk. The earlier conjunctive tsquery gate matched zero rows anywhere in the corpus for a realistic multi-concept query, so the lexical channel contributed nothing and hybrid search ran on the semantic half alone. The disjunctive rewrite only touches the query’s spaced AND operator, not an operator character living inside a search term — a naive substitution corrupted URLs with query strings, which Slack-sourced evidence carries routinely.
  • Policy evidence reserves a result slot when authorized. Exact account, opportunity, and contact records are included as cited grounding without displacing the ranked quality set.
  • Context packing reserves at least eight characters for each ranked or mandatory grounding item; an impossible budget fails explicitly rather than silently dropping evidence.
  • Citation resolution reauthorizes the current evidence row and checks immutable manifest membership. Missing, stale, unauthorized, and out-of-manifest citations share one opaque denial.

A golden-retrieval regression eval gates CI. pnpm eval:deterministic is wired into CI as its own step, after the unit/contract/integration suite; it replays a small hand-authored set of opportunity/query cases against a real Postgres retriever and reports macro recall, macro precision, and permission leakage. At HEAD it holds macroRecallAtK 0.5, macroPrecisionAtK 0.2, and permissionLeakage 0 — the gate only requires recall at or above 0.5, so today’s score sits exactly on that floor with no headroom (the comparison carries a small float tolerance so representation noise alone can’t turn it red). The remaining recall loss is not source crowding: two golden items still lose to sibling chunks within their own source type’s internal ranking, and CI’s mock embedding gateway means the semantic half of hybrid search is not a meaningful signal in that environment. Both remain open items.

HNSW is planned, not shipped. The shipped semantic path is exact cosine over the authorized subset. Any future ANN adapter must return candidate IDs only, rejoin current authorization, rerank by exact cosine, keep exact search as oracle, fallback, and kill switch, and never share one global graph across security domains. It stays shadow-only until zero-leakage, policy-inclusion, citation-authorization, recall, underfill, latency, replication, rebuild, and recovery gates pass.

06 · Security notes

Fail closed at the boundaries that matter.

Permission enforcement and opaque denial

Canonical grants bind persona, account, source type, restricted-account access, sensitive-pricing access, and fixture provenance. Security-barrier views and query predicates apply those dimensions before returning text, locators, scores, counts, or vectors. The workflow also binds the run to the requested persona and opportunity. Before generation, the scope hash is independently recomputed and checked against the manifest.

recordOpaqueDenial and opaqueCitationDenial deliberately avoid account, source, evidence, locator, recommendation, and citation facts. Trace completeness validation rejects denial traces that contain such details, so BOLA/permission failures do not become a side channel through errors or observability.

Sensitivity classification and approvals

Ingestion does not trust one “sensitive” column. Effective sensitivity combines source type, source access level, restricted-opportunity state, pricing-note language, and the canonical policy text/hash; pricing requires the policy’s sensitive-pricing rule to be provable. Separately, opportunity_policy_facts derives structured commercial/legal signals from pricing rows and opportunity restrictions. Edits are rescanned by deterministic concept pairs—for example, a liability subject plus change language, or a commercial benefit plus commitment language.

Approval requirements are stored as category entries with eligible authorities and dependencies. Authority membership is account-scoped and rechecked at decision time. A discount above 10% requires deal desk; above 15% adds a separate sales-leader entry, so two distinct subject-entry decisions are required. Legal terms require a legal reviewer; evidence concerns accept account owner or sales leader; customer concessions depend on earlier entries and require the account owner. Decisions, approved/original payloads, hashes, diffs, and replay results are immutable.

Anti-hallucination and prompt-injection defenses

Evidence identity is code-owned

The model must copy a complete citation tuple, but runtime canonicalization restores manifest-owned ID, evidence ID, and locator. Unknown, duplicate, stale, unauthorized, and forged references fail validation.

Support is semantic but bounded

Validation checks exact structured fields, material anchors, polarity, predicates, and tightly constrained paraphrases. Unsafe instruction-like prose and ungrounded customer-facing recommendations are rejected.

Evidence is inert data

Prompts state that evidence instructions, roles, tool requests, schemas, and citation forgeries are non-executable. Fixed delimiters separate instructions from untrusted records and specialist artifacts.

Delimiter escape is contract-tested

tests/contract/agents.test.ts names the case “cannot let an evidence record close the fixed inert-data delimiter”. Reserved BEGIN/END markers are replaced with explicit escaped-delimiter tokens before prompt construction.

State persistence, recovery, and inspection

PostgreSQL is the system of record: identities and grants, immutable evidence versions and embeddings, run state and version, budgets and provider attempts, manifests, outbox delivery state, step leases, checkpoints, specialist artifacts, claims and citations, approval snapshots and decisions, briefs, audit events, run events, and trace spans. Redis/BullMQ delivers work; it is never the recovery authority.

Recovery is the mechanism drawn in §04: the reconciler inspects published and claimed outbox commands against BullMQ state, fences its recovery with claim tokens, republishes only safe work, and resumes from the checkpoints already written. Trace projection records authorization, retrieval, every model call, validation, guardrails, usage and repair, degradation, approval requirements and decisions, and finalization; append-only triggers and stable IDs make that projection idempotent, so an operator reading the timeline sees the same history a replay would produce.

Synthetic Slack-style updates: production and ingestion

scripts/generate-slack-fixtures.ts accepts only live openrouter or ollama configuration—mock is rejected. It asks for exactly three clearly synthetic updates per opportunity: a reinforcing fact, missing context, and ambiguity/conflict. It validates row IDs, account/opportunity bindings, chronology between the latest evidence date and close date, synthetic notices, access levels, control characters, and category coverage before replacing the TSV.

The checked-in fixtures/cato/slack/generation.json records an observed OpenRouter run using google/gemini-3.5-flash-lite, native-schema output, two calls, zero repairs, 3,444 input tokens, 2,381 output tokens, and 5,825 total tokens. It also records prompt/schema/source/output SHA-256 hashes, pinned source commit, generation time, reviewed status, and row-level context categories for all nine updates.

pnpm ingest:records parses that provenance with the fixture set, verifies live-generation completeness and source/output binding, chunks the Slack records with their locators, provenance, effective classification, reliability, and policy hash, and upserts immutable documents/evidence. pnpm index:embeddings then embeds the canonical Slack locator prefix alongside the other sources. Regeneration therefore requires re-ingestion and re-indexing.

A dedicated diagnostic, samples/slack-impact-comparison.{json,md}, demonstrates the mandatory subtask’s with/without-Slack-authorization comparison end to end. Toggling one requester’s Slack grant off and back on confirms the retrieval-level mechanism works: removing authorization mechanically drops the Slack chunk from the candidate pool and backfills the next-best candidate, with everything else about the run identical. Across the four live with-Slack-authorized OpenRouter runs it has visibility into, no finalized Deal Brief cites Slack evidence — reported honestly rather than fabricated. In one of those runs it traces exactly where a Slack update drops out of the pipeline: ingested, correctly authorized, retrieved competitively (rank 13–16 of about 27 candidates across the sampled runs, with a fusion score in the same band as many Gong transcript entries), prompted in full at its complete chunk size, and validated as a supported claim by a specialist agent — yet the Negotiation Strategy Agent still re-synthesizes that section’s claims from the shared evidence pool under fresh claim IDs rather than forwarding a specialist’s claim verbatim, so the validated Slack claim has no path into the brief. The volume asymmetry the report names as the retrieval-side contributor — gong_transcript’s previously uncapped candidate window — is now closed (see §05); giving the strategy synthesis step a reason to draw from every authorized source type that returned evidence is recorded as the remaining path to a Slack-cited brief, not implemented here.

Secrets and honest limitations

Database, Redis, session, provider, and model configuration comes from validated server-side environment variables. .env and .env.local are gitignored, credentials are excluded from model diagnostics, and logging redaction suppresses common secret and authorization fields.

Not production-hardened: there is no provider cost/spend accounting beyond per-run call and deadline budgets, per-call context/output token budgets, and persisted token usage; no documented API/user/provider rate-limiting policy; no secrets-manager or automatic rotation integration; no enterprise identity provider; and no production-grade PII service. These are deployment gaps, not controls to infer from the current code.

Brief sections are grounded-or-omitted, not guaranteed-populated. Every section in a finalized DealBrief is generate-then-validate: validateDealBrief keeps only claims it can tie back to an authorized evidence unit and drops the rest, so a section with no supportable claim renders empty rather than fabricated. With the small model this project runs against by default (google/gemini-3.5-flash-lite), that means Stakeholder Map and Recommended Next Actions — the two sections with the strictest per-item grounding requirements (a named person plus a supported identity claim; an action tied to a supported rationale) — do not come back populated on every regeneration, even though the retrieved evidence would support them. Regenerating samples/normal-opportunity-brief.json and samples/restricted-opportunity-brief.json for this submission took roughly 50 live runs combined across both opportunities before both sections landed populated, without any other section going empty, in the same run. This is the tradeoff working as intended: the system never invents a stakeholder or an action to fill a section, so an empty section is a true signal about what this run’s model output could support, not a defect being hidden.

08 · Production readiness

A strong recovery core; an intentionally incomplete operating envelope.

Scalability

What it is: keeping the system responsive as users, simultaneous briefs, and evidence rows increase.

Why it matters

  • A design that works for one demo can slow down or fail when many teams use it together.

Already works

  • Separate API and workers: web requests stay quick while workers handle slow retrieval and generation.
  • Queue: holds bursts of work until a worker is available.
  • Bounded work: each run has limits, so one brief cannot consume unlimited search or model capacity.

Before production

  • Load test: run many briefs at once to find the point where response time or errors become unacceptable.
  • Soak test: keep realistic traffic running for hours or days to reveal memory leaks and growing backlogs.
  • Safe queue depth: define how many waiting jobs are acceptable before adding workers or slowing new requests.
  • Database capacity: measure how many connections and searches PostgreSQL can handle safely.
  • Worker scaling rules: define when workers are added or removed from measured queue and latency signals.
  • Fast vector index: yes, ANN/HNSW is likely needed when a user’s authorized search scope reaches millions of rows. If millions of total rows filter down to a small authorized subset, exact search may still be safer and fast enough.

High availability

What it is: continuing safely when an application process, queue, or database instance fails.

Why it matters

  • A restart must not lose a brief, repeat an approval, or advance the same run twice.

Already works

  • Interrupted work recovery: yes—if a worker stops, its lease expires and another worker continues from the saved PostgreSQL checkpoint.
  • Idempotent commands: receiving the same command twice does not repeat completed work.
  • Version checks: two workers cannot both commit conflicting state changes.

Before production

  • Redundant databases: managed PostgreSQL and Redis need standby instances in another availability zone.
  • Failover and restore drills: prove the standby and backups work before an incident.
  • Safe schema rollout: define how database changes are deployed and reversed without breaking live workers.
  • Disaster-recovery target: decide how much data loss and downtime the business can accept.

Monitoring

What it is: showing operators whether the system is healthy, slow, stuck, or producing errors.

Why it matters

  • Saved diagnostic data is useful only if someone can find a problem and act before users report it.

Already works

  • Run timeline: records authorization, retrieval, model calls, checks, approvals, failures, and completion.
  • Health endpoints: report whether the API and its required dependencies are reachable.

Before production

  • Telemetry export: send metrics and traces to an operations platform.
  • Dashboards and alerts: make queue growth, errors, slow runs, dead letters, and provider failures visible.
  • Service-level objectives: define acceptable reliability and response-time targets.
  • Runbooks: give on-call staff exact steps for each alert.

Secrets

What it is: protecting database passwords, session keys, and model-provider credentials.

Why it matters

  • A leaked credential can expose customer evidence or let an attacker spend money through a provider account.

Already works

  • Server-only configuration: credentials are never sent to the browser.
  • Startup validation: the server refuses invalid or missing security settings.
  • Redaction: common secret fields are removed from logs and model diagnostics.

Before production

  • Secret manager or workload identity: provide credentials without storing long-lived keys in files.
  • Least privilege: each service receives only the access it needs.
  • Rotation and audit: replace keys automatically and record who accessed them.
  • Revocation plan: define how a leaked credential is disabled immediately.

Operational support

What it is: giving support staff safe tools to inspect and recover customer runs.

Why it matters

  • Support should not need direct database access to explain, cancel, recover, or quarantine a bad run.

Already works

  • Inspectable runs: timelines, approvals, and diagnostic codes show what happened.
  • Cancellation: a requester can stop live work through a defined workflow transition.
  • Recovery states: dead-letter and retry outcomes are recorded rather than hidden.

Before production

  • Scoped support console: expose only the customer data an operator is allowed to inspect.
  • Replay and quarantine: safely retry recoverable work or isolate suspicious work.
  • Retention and deletion: enforce how long customer data remains stored.
  • Escalation and emergency access: assign owners and audit every exceptional action.

Safety and governance

What it is: controlling who sees confidential evidence and who is accountable for sensitive recommendations.

Why it matters

  • The assistant handles private deal information and can influence pricing, legal, and customer commitments.

Already works

  • Database authorization: forbidden evidence is filtered before search.
  • Citation checks: unsupported claims are rejected.
  • Safety checks: unsafe instructions in evidence are treated as data, not commands.
  • Human approvals: policy-sensitive recommendations cannot finalize without the required authority.

Before production

  • Threat model and penetration test: identify attack paths and verify defenses.
  • Privacy and residency review: decide which data may be sent to each provider and region.
  • PII evaluation: measure detection of organization-specific personal information.
  • Adversarial prompt testing: test malicious or misleading evidence at scale.
  • Policy ownership: assign people to review approval rules and user permissions regularly.

Cost and capacity

What it is: keeping model spend and processing time predictable as usage grows.

Why it matters

  • A provider change, retry storm, or traffic spike can increase both latency and cost unexpectedly.

Already works

  • Attempt and time limits: stop a run from retrying forever.
  • Context and output limits: cap how much text each model call can process or return.
  • Usage records: save actual token counts for later analysis.

Before production

  • Currency-level accounting: convert provider usage into actual money spent.
  • Team budgets: cap or alert on spend by tenant or team.
  • Forecasts and anomaly alerts: detect unusual growth before a bill arrives.
  • Measured model routing: choose models only after comparing quality, latency, and price for each agent task.

Possible later improvements

These are useful ideas, not current features. Each card starts with what the idea means, then explains why it should wait.

Adaptive ANN / HNSW

What it is: a fast approximate vector index that finds likely matches without comparing every row.

Why later: it is probably needed when one authorized search scope reaches millions of rows. It must still recheck permissions and exact similarity before returning evidence; total database size alone is not enough reason to enable it.

PII defense in depth

What it is: an extra check for names, contact details, identifiers, and other personal information before data reaches a model or final brief.

Why later: a private detector such as Presidio and a separate checking agent can both flag possible PII, but neither should make the final decision alone. Deterministic rules and human review remain the authority for risky cases.

Cross-encoder reranking

What it is: a second model that rereads the query and top search results together to improve their final order.

Why later: it adds latency, cost, and more evidence exposure. Add it only if measured retrieval quality is not good enough without it.

Synthetic labeled evaluations

What it is: model-generated test questions and expected answers used to expand retrieval and brief-quality evaluation.

Why later: generated labels can be wrong or copy training data. They need provenance, contamination checks, human review, and clear acceptance thresholds before they influence quality decisions.
