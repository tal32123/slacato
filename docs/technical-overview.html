01 · Business context

One brief for the moment before a negotiation.

A seller preparing for a commercial negotiation has to reconcile CRM facts, recent calls, stakeholder dynamics, account-team updates, pricing notes, and deal-desk policy—often under time pressure and with different access rules for each source. The system accepts an opportunity and requester identity, assembles the evidence that person is allowed to use, and produces a concise preparation brief with traceable support.

The objective is not autonomous negotiation. It is decision support: surface the buyer’s goals, the current commercial state, risks, stakeholders, missing information, and next actions while making uncertainty visible. Pricing, legal, customer-facing concessions, and low-confidence material remain subject to deterministic policy and human authority.

Reduce preparation time

Fan out focused analysis across conversation, stakeholder, and commercial evidence, then synthesize one coherent brief.

Keep evidence inspectable

Claims link to immutable authorized evidence; API and UI render stable labels such as source=<file>, id=<value>.

Keep people accountable

If a recommendation needs approval—for example, a large discount—the brief waits for the right person to approve or reject it.

02 · Architecture

Thin apps around durable domain and infrastructure seams.

The browser requests work. The API checks access. The worker builds the brief. Core holds the business rules; infrastructure connects them to storage, queues, search, and models.

Updated

Logical view

Authorized hybrid RAG

Authorization narrows the corpus before exact CRM, full-text, and vector search. Reciprocal-rank fusion produces a frozen evidence manifest that every downstream step must honor.

Durable typed orchestration

The orchestrator supplies typed AgentContext to Conversation, Stakeholder, and Commercial, checkpoints their artifacts, and invokes Strategy with typed StrategyArtifacts.

Validation + guardrails

Schema, citation ownership, semantic support, unsafe-language, and approval-policy checks run in deterministic code around model output.

HITL before output

The human-in-the-loop quorum must resolve every required approval before the web brief, API read model, or reviewer export can expose finalized output.

Trace + audit projection

Retrieval, model, validation, approval, and final-output events feed one persisted reviewer timeline rather than separate, unverifiable logs.

Asymmetric failure boundary

Recoverable specialist degradation is explicit and checkpointed; unsafe commercial or synthesis failure stops the run instead of producing a misleading brief.

Updated

Deployment view

The API proves who may request work, the worker performs it, PostgreSQL preserves recovery authority, the model gateway contains provider access, and operational credentials and telemetry stay behind explicit deployment boundaries.

Why one browser origin?

The web gateway serves the interface and forwards API calls under one origin, so secure session cookies do not need cross-origin exceptions.

Why split API and worker?

The API can answer after recording a command. Slow retrieval and model calls run in the worker without holding an HTTP request open.

Why does PostgreSQL own recovery?

Workflow state and checkpoints survive process or queue loss. Redis can be rebuilt without losing which durable step runs next.

Why one model gateway?

Every provider call crosses one boundary where request contracts, retries, validation, usage, and diagnostics are applied consistently.

How are secrets supplied?

The Secrets manager injects scoped credentials into the API, worker, and model gateway. Reviewer browser and web gateway receive no database or provider credentials.

What feeds operations?

API, worker, PostgreSQL, Redis, and model gateway all emit health, metrics, traces, and diagnostics to Monitoring + telemetry.

03 · Agent roles

Four focused agents. One negotiation brief.

The agents have no tools. Not "few" - none: the shared input type deliberately exposes no repository, transport, tool, or other-agent handle. The workflow hands each specialist a permission-checked evidence bundle and takes back a structured object, and that is the whole interface. It is a security decision before it is a design one: an agent with no way to fetch anything cannot widen its own permissions, so the authorization decision made before generation is the one that holds - there is no second path to the data for a prompt injection to find.

Conversation Intelligence

What: finds buyer goals, objections, urgency, and open questions in calls and Slack updates.
Why: the buyer’s own signals should shape the negotiation plan.
Inputs: authorized Gong call summaries, Gong transcripts, and Slack updates.
Tools: none. It is handed its evidence and returns a structured object; retrieval, policy, and citation checks run in code around it.

Stakeholder Map

What: identifies champions, decision-makers, blockers, and missing relationships.
Why: a good commercial plan fails if the wrong people are engaged.
Inputs: authorized Salesforce contacts, Gong summaries and transcripts, and Slack updates.
Tools: none. Same contract as every specialist: evidence in, a stakeholder object out, no way to fetch more.

Commercial Analysis

What: reviews pricing, policy, legal concerns, and sensitive concessions.
Why: high-impact terms need focused scrutiny and human approval.
Inputs: authorized Salesforce records, pricing notes, and Deal Desk policy evidence.
Tools: none. Evidence in, a commercial object out. The approval policy that gates concessions is deterministic code, not something this agent decides.

Negotiation Strategy

What: combines the three specialist views into the final brief and next actions.
Why: the seller needs one prioritized, evidence-backed view of the deal.
Inputs: all three validated specialist outputs and the full authorized evidence list.
Tools: none. It sees only the three validated specialist outputs and the authorized evidence list, and returns the brief.

Updated

Executable contracts and failure disposition

Each role is an executable typed boundary, not only a prompt persona. The same frozen, authorized evidence manifest binds input, output validation, citations, and the checkpoint written for that invocation.

AgentExecutable contractEvidence and validation constraintsFailure disposition
Conversation AgentContext → ConversationArtifact Receives only authorized Gong summaries, transcripts, and Slack updates. Manifest binding, strict schema, citation ownership and support checks apply; the serialized artifact is capped at 6,000 bytes. Degraded. Commercial AgentContext → CommercialArtifact Receives only authorized Salesforce, pricing, and policy evidence. Manifest, strict schema, citation, support, commercial-term and approval inputs are validated; the serialized artifact is capped at 6,000 bytes. Fatal. End the run as commercial_specialist_failed; commercial uncertainty cannot be silently downgraded.
Strategy StrategyArtifacts → DealBrief Receives the three validated specialist artifacts plus the same authorized evidence manifest. It must return the canonical nine-section schema; citation, support, safety and policy validation run before approval routing. Fatal. End the run as strategy_generation_failed; no partial final brief is emitted.

Fan-out, checkpoint, fan-in: missing specialists start together under Promise.allSettled. The workflow persists each outcome in deterministic Conversation → Stakeholder → Commercial order, then fans the three checkpoints into Strategy. The failure policy is deliberately asymmetric: Conversation and Stakeholder may continue as explicit empty degraded artifacts, while Commercial and Strategy failures are fatal.

04 · Run lifecycle

A clear path from request to reviewed brief.

How a brief is created

The system follows a fixed sequence, saves progress after every stage, and can resume after an interruption without starting over.

How each source is chunked

Chunking follows the source’s natural structure rather than applying one arbitrary text size to every document.

SourceChunkingWhy
Salesforce recordsOne account, opportunity, or contact record per chunk; no further splitting.Keeps related fields together and gives each structured record a stable citation target.
Gong summariesOne call-summary record per chunk; no further splitting.The summary is already a concise, structured unit for one call.
Gong transcriptsSix-turn windows with a one-turn overlap; every window repeats the transcript heading and metadata.Preserves conversational context at window boundaries and keeps each excerpt attributable.
Slack updatesOne dated account-team update per chunk; no further splitting.The short update remains intact and attributable to its source record.
Pricing notesOne pricing-note record per chunk; no further splitting.Keeps requested terms, approval status, and commercial context together.
Deal Desk policySplit at Markdown headings. Sections over 512 characters become smaller rule groups that repeat the heading.Makes each rule group self-contained and small enough to quote in full without losing its policy context.

How work is routed between agents

After evidence is selected, three specialist agents run in parallel. Their saved findings flow into the strategy agent, then code validates the draft and routes any required approval.

Updated

Live-model controls

Live generation runs behind deterministic authorization, shape, retry, and durable-run boundaries. These are application controls; they do not imply provider-side limits that the adapter does not send.

Authorized context selection

Exact canonical CRM evidence and Authorized hybrid RAG results are selected only from the requester’s allowed deal and source scope, then frozen in the run manifest. Model prompt assembly accepts at most 20 authorized evidence records inside a 24,000-character retrieval context and trims any one evidence record to 6,000 characters.

Artifact and schema limits

Conversation and Commercial artifacts are capped at 6,000 serialized bytes; Stakeholder is capped at 8,192. Persisted artifacts and raw JSON responses stop at 128 KiB. Strict JSON parsing also caps nesting at 32 levels and 10,000 nodes, followed by full local schema and evidence-support validation.

Invocation and run budgets

One agent invocation may make at most 4 calls, including no more than 2 schema repairs and 1 transport retry. The shared run budget allows 24 calls and has a persisted 600-second deadline, so a replacement worker inherits the same deadline rather than resetting it.

Usage and provider parameters

Every durable attempt records reported input and output token usage with its operation and provider diagnostics. The adapter leaves temperature and topP at provider defaults. It sends no provider-side maxOutputTokens and enforces no aggregate currency cap; local byte/schema bounds plus call and deadline limits are the current controls.

OpenRouter embeddings: the default indexing profile is OPENROUTER_EMBEDDING_DIMENSION=1536. The setting must be an integer from 1 through 16000. It may be omitted only for the default openai/text-embedding-3-small model, whose required dimension is fixed at 1,536; selecting a different embedding model requires its explicit matching dimension so incompatible vectors are rejected rather than compared.

05 · Trust and security

Protect the data. Verify the answer. Keep people accountable.

Deal and source access

What: a user may open only deals and source types assigned to them.
Why: strategic deals contain restricted customer, pricing, and legal information.
How: PostgreSQL permission grants are checked before search and again before evidence reaches an AI model; denied requests reveal no deal details.

Evidence-backed claims

What: every factual statement shown to the seller must cite an allowed source.
Why: invented amounts, dates, stakeholders, or commitments can damage a live negotiation.
How: the agent returns each claim with a citation ID. Code matches it to the run’s frozen authorized evidence list, restores the trusted source label and locator, and checks that material names, amounts, dates, and meaning are supported by the cited text. Missing, unauthorized, or unsupported claims are removed.

Human approval before action

What: an accountable person must approve sensitive recommendations before the brief can finalize.
Why: these are high-value deals with real pricing, legal, and customer commitments.
How: the workflow pauses and routes each issue to Deal Desk, Sales leadership, legal, or the account owner; it continues only after every required approval is recorded.

Review and recovery history

What: reviewers can see which evidence, agents, and decisions produced the brief.
Why: the business must explain outcomes and recover interrupted work without repeating approvals.
How: PostgreSQL stores run progress, retrieved evidence, model calls, approvals, and the final brief; a replacement worker resumes from the last saved stage.

Generated Slack evidence

The canonical dataset is fixtures/cato/slack/account_team_updates.tsv; its reviewed live-generation record is fixtures/cato/slack/generation.json. It contains three clearly synthetic account-team updates per opportunity: one reinforcing fact, one missing-context signal, and one ambiguity or conflict.

Fixture loading validates the strict TSV shape, unique IDs, synthetic notices, opportunity/account bindings, chronology, per-opportunity coverage, and the reviewed output hash in generation provenance before ingestion can proceed. Ingestion stores each row as sourceType=slack, classifies its declared source_access_level, and preserves the stable locator slack/account_team_updates.tsv#<update_id>. Retrieval then requires an effective slack source grant and rechecks the run’s authorized evidence manifest before any row reaches an agent.

07 · Production readiness

A strong recovery core; an intentionally incomplete operating envelope.

Scalability

What it is: keeping the system responsive as users, simultaneous briefs, and evidence rows increase.

Why it matters

  • A design that works for one demo can slow down or fail when many teams use it together.

Already works

  • Separate API and workers: web requests stay quick while workers handle slow retrieval and generation.
  • Queue: holds bursts of work until a worker is available.
  • Bounded work: each run has limits, so one brief cannot consume unlimited search or model capacity.

Before production

  • Load test: run many briefs at once to find the point where response time or errors become unacceptable.
  • Soak test: keep realistic traffic running for hours or days to reveal memory leaks and growing backlogs.
  • Safe queue depth: define how many waiting jobs are acceptable before adding workers or slowing new requests.
  • Database capacity: measure how many connections and searches PostgreSQL can handle safely.
  • Worker scaling rules: define when workers are added or removed from measured queue and latency signals.
  • Fast vector index: yes, ANN/HNSW is likely needed when a user’s authorized search scope reaches millions of rows. If millions of total rows filter down to a small authorized subset, exact search may still be safer and fast enough.

High availability

What it is: continuing safely when an application process, queue, or database instance fails.

Why it matters

  • A restart must not lose a brief, repeat an approval, or advance the same run twice.

Already works

  • Interrupted work recovery: yes—if a worker stops, its lease expires and another worker continues from the saved PostgreSQL checkpoint.
  • Idempotent commands: receiving the same command twice does not repeat completed work.
  • Version checks: two workers cannot both commit conflicting state changes.

Before production

  • Redundant databases: managed PostgreSQL and Redis need standby instances in another availability zone.
  • Failover and restore drills: prove the standby and backups work before an incident.
  • Safe schema rollout: define how database changes are deployed and reversed without breaking live workers.
  • Disaster-recovery target: decide how much data loss and downtime the business can accept.

Monitoring

What it is: showing operators whether the system is healthy, slow, stuck, or producing errors.

Why it matters

  • Saved diagnostic data is useful only if someone can find a problem and act before users report it.

Already works

  • Run timeline: records authorization, retrieval, model calls, checks, approvals, failures, and completion.
  • Health endpoints: report whether the API and its required dependencies are reachable.

Before production

  • Telemetry export: send metrics and traces to an operations platform.
  • Dashboards and alerts: make queue growth, errors, slow runs, dead letters, and provider failures visible.
  • Service-level objectives: define acceptable reliability and response-time targets.
  • Runbooks: give on-call staff exact steps for each alert.

Secrets

What it is: protecting database passwords, session keys, and model-provider credentials.

Why it matters

  • A leaked credential can expose customer evidence or let an attacker spend money through a provider account.

Already works

  • Server-only configuration: credentials are never sent to the browser.
  • Startup validation: the server refuses invalid or missing security settings.
  • Redaction: common secret fields are removed from logs and model diagnostics.

Before production

  • Secret manager or workload identity: provide credentials without storing long-lived keys in files.
  • Least privilege: each service receives only the access it needs.
  • Rotation and audit: replace keys automatically and record who accessed them.
  • Revocation plan: define how a leaked credential is disabled immediately.

Operational support

What it is: giving support staff safe tools to inspect and recover customer runs.

Why it matters

  • Support should not need direct database access to explain, cancel, recover, or quarantine a bad run.

Already works

  • Inspectable runs: timelines, approvals, and diagnostic codes show what happened.
  • Cancellation: a requester can stop live work through a defined workflow transition.
  • Recovery states: dead-letter and retry outcomes are recorded rather than hidden.

Before production

  • Scoped support console: expose only the customer data an operator is allowed to inspect.
  • Replay and quarantine: safely retry recoverable work or isolate suspicious work.
  • Retention and deletion: enforce how long customer data remains stored.
  • Escalation and emergency access: assign owners and audit every exceptional action.

Safety and governance

What it is: controlling who sees confidential evidence and who is accountable for sensitive recommendations.

Why it matters

  • The assistant handles private deal information and can influence pricing, legal, and customer commitments.

Already works

  • Database authorization: forbidden evidence is filtered before search.
  • Citation checks: unsupported claims are rejected.
  • Safety checks: unsafe instructions in evidence are treated as data, not commands.
  • Human approvals: policy-sensitive recommendations cannot finalize without the required authority.

Before production

  • Threat model and penetration test: identify attack paths and verify defenses.
  • Privacy and residency review: decide which data may be sent to each provider and region.
  • PII evaluation: measure detection of organization-specific personal information.
  • Adversarial prompt testing: test malicious or misleading evidence at scale.
  • Policy ownership: assign people to review approval rules and user permissions regularly.
Updated

Cost and capacity

What it is: keeping model spend and processing time predictable as usage grows.

Why it matters

  • A provider change, retry storm, or traffic spike can increase both latency and cost unexpectedly.

Already works

  • Call and deadline limits: stop one invocation or run from retrying forever.
  • Local shape limits: bound selected context, serialized artifacts, and strict JSON complexity; the adapter does not claim or send a provider-side output-token cap.
  • Usage records: save reported input and output token counts for later analysis.

Before production

  • Currency-level accounting: convert provider usage into actual money spent.
  • Team budgets: cap or alert on spend by tenant or team.
  • Forecasts and anomaly alerts: detect unusual growth before a bill arrives.
  • Measured model routing: choose models only after comparing quality, latency, and price for each agent task.

Possible later improvements

These are useful ideas, not current features. Each card starts with what the idea means, then explains why it should wait.

Adaptive ANN / HNSW

What it is: a fast approximate vector index that finds likely matches without comparing every row.

Why later: it is probably needed when one authorized search scope reaches millions of rows. It must still recheck permissions and exact similarity before returning evidence; total database size alone is not enough reason to enable it.

PII defense in depth

What it is: an extra check for names, contact details, identifiers, and other personal information before data reaches a model or final brief.

Why later: a private detector such as Presidio and a separate checking agent can both flag possible PII, but neither should make the final decision alone. Deterministic rules and human review remain the authority for risky cases.

Cross-encoder reranking

What it is: a second model that rereads the query and top search results together to improve their final order.

Why later: it adds latency, cost, and more evidence exposure. Add it only if measured retrieval quality is not good enough without it.

Synthetic labeled evaluations

What it is: model-generated test questions and expected answers used to expand retrieval and brief-quality evaluation.

Why later: generated labels can be wrong or copy training data. They need provenance, contamination checks, human review, and clear acceptance thresholds before they influence quality decisions.
